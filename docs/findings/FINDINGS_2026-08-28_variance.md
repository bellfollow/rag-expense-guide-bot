## 1. 발단 — 4번의 판정이 전부 노이즈였다

`flag` 정확도가 0%였다. 네 번 수정하고 각각 **1회씩** 측정해 개선/악화를 판정했다.

| 수정 | 내용 | 측정 macro | 그때의 판정 |
|---|---|---|---|
| A | 분류 프롬프트에 "정보 부족 → 확인필요" 규칙 | 50% | 개선했으나 단일 클래스 붕괴 |
| B | 컴플라이언스가 flag를 뒤집게(override) | 82% | 성공 |
| C | override 코드 게이트 + 검색 fallback | 67% | ②가 순손실, 롤백 |
| D | 검색 fallback 롤백 | 67% | 회복 실패, 원인 불명 |

D에서 이상한 점이 있었다. C에서 성공했던 `r004`가 실패하고 대신 `r002`가 성공했다.
**코드 변경으로 설명되지 않는 결과였다.**

코드를 한 글자도 바꾸지 않고 3번 돌렸다.

```
run1  macro 82%   지원불가 2/3   override가 잡은 건: r001, r004
run2  macro 67%   지원불가 1/3   r001
run3  macro 48%   지원불가 0/3   없음
```

**분산 34%p. B·C·D가 전부 이 범위 안에 들어간다.** 네 번의 판정 중 무엇에도 근거가 없었다.

### 어떻게 알아챘나 — 집계값이 아니라 구성

발견의 계기는 지표가 아니라 **설명되지 않는 개별 사례**였다.
macro recall만 봤다면 "67% → 67%, 변화 없음"으로 넘어갔을 것이다.

러너가 건별 `override 효과` 목록을 찍고 있었기에 `r004 → r002` 교체가 보였다.
집계 지표만 출력했다면 지금도 노이즈를 쫓고 있었을 것이다.

> **집계값이 같아도 구성이 다르면 의심해야 한다.**

## 2. 국소화 — 어느 단계에서 시작하는가

추측을 멈추고, 같은 이미지를 3번씩 태워 **단계별 출력의 동일성**(정확도가 아니라)을 비교했다.
3장 × 3회 = 9콜, 약 3원.

### 결정적 증거 — 성수주유소 영수증

```
① 추출  vendor    "성수주유소"     1값 ✅
① 추출  item      "휘발유 주유"    1값 ✅
① 추출  amount    85000           1값 ✅
① 추출  date      "2026-08-03"    1값 ✅
        ↓ 입력이 글자 하나 다르지 않다
② 분류  flag      "확인필요" / "지원불가"   🚨
② 분류  confidence "low"           1값
```

**입력이 완전히 동일한데 분류가 갈린다.** 분류 단계 자체가 흔들린다는 직접 증거다.

동시에, 나머지 2장은 추출부터 흔들렸다.

```
"(유)풍차주소"  ↔  "(유)풍차주유소"                      OCR 오독이 실행마다 갈림
"주차 요금"     ↔  "주차요금"                            띄어쓰기
"아마노코리아(주) 고양터미널" ↔ "고양터미널 (아마노코리아(주))"   순서
```

`amount`·`date`는 3장 모두 안정. **숫자는 흔들리지 않고 자연어만 흔들린다.**

### 그때 내가 틀렸던 것

31장 측정에서 금액 `94/94/94`, 날짜 `97/97/97`을 보고 "추출은 안정적"이라고 단정했다.
그것은 **정확도**이지 **동일성**이 아니었고, 분류 단계가 실제로 받는 입력인
`item`·`vendor`는 **한 번도 측정한 적이 없었다.**

## 3. 원인 — 흔들림은 정보 부족의 증상이다

안 흔들리는 것과 흔들리는 것을 나란히 놓으면 답이 보인다.

```
안 흔들림   금액, 날짜        영수증에 답이 인쇄돼 있다
흔들림      sub_item, flag    영수증에도 taxonomy에도 답이 없다
```

주유비가 지원 불가라는 근거는 가이드라인에만 있다.

> L248 — "자가 이용 시 동일구간 내 대중교통비 정액을 기준으로 집행한다.
> **유류비는 지원되지 않으며**, 이 때 톨비 영수증을 제출하여야 한다."

그런데 분류 단계는 RAG를 쓰지 않고 `RECEIPT_CATEGORY_TAXONOMY`만 본다.
거기에 이 조항이 없다. 모델은 답을 모르니 비슷한 확률의 후보
(`해당없음` / `국내여비(운임)` / `소모품비`) 사이에서 매번 다르게 찍는다.
`confidence`가 `low`로 고정된 것이 이를 뒷받침한다.

**`temperature=0`으로 막을 수 없다. 정보를 줘야 한다.**

### 죽어 있던 규칙

수정 A에서 넣은 Rule 4-1은 이랬다.

```
4-1. "지원불가"는 영수증에 실제로 인쇄된 사실만으로 금지 조항에 걸릴 때만 쓴다.
```

**참조할 금지 조항 목록이 taxonomy에 없어서 실행 불가능한 규칙이었다.**
`지원불가`를 낼 수 있는 경로가 닫혀 있었고, 그래서 A는 전 건을 `확인필요`로 밀어
단일 클래스로 붕괴했다(macro 50%, 다수결 베이스라인과 동일).

## 4. 수정 E — 금지 조항을 두 그룹으로 나눠 제공

`RECEIPT_CATEGORY_TAXONOMY`의 주의사항 블록만 교체했다. **분류 단계에 RAG는 붙이지 않았다** —
고치려는 것이 불안정성인데 검색을 추가하면 불안정 요인이 하나 더 늘기 때문이다.

핵심은 **영수증만으로 판정 가능한지**로 목록을 가른 것이다.

```
[영수증만으로 판정 가능 → 지원불가로 판정하라]
  유류비 · 주차비 · 렌터카 · 출장지 내 택시
  범용성 기자재(PC/노트북/태블릿) · 귀금속

[영수증만으로 판정 불가 → 확인필요로 두라]
  회의비 · 협약기간 밖 집행 · 친족 간 거래
```

지금까지 이 둘이 섞여 있어서, 모델은 회의비 조항 하나로 모든 식당을 거절하거나(A 이전)
명백한 유류비를 판단 유보로 미뤘다(A 이후).

### 결과 — 분산이 사라졌다

3장 × 3회 재측정:

```
E 이전   flag: "확인필요" / "지원불가"   🚨    confidence: low
E 이후   flag: "지원불가"                1 ✅   confidence: high
```

`confidence`가 `low → high`로 바뀐 것이 결정적이다.
모델이 근거를 갖게 되어 확신하는 것이고, 이전에는 몰라서 동전을 던지고 있었다.

31장 × 3회: **macro recall 100% / 100% / 100%. 분산 0%p.**

### 부수 확인 — ①(추출)은 고치지 않아도 됐다

```
r002   vendor 🚨 흔들림          →  flag 1 ✅
r004   vendor 🚨 + item 🚨 흔들림 →  flag 1 ✅
```

**추출이 흔들려도 하류로 전파되지 않는다.** 분류가 근거를 갖게 되니 표기 차이에 둔감해졌다.
추출 프롬프트를 건드렸다면 안정적이던 금액·날짜만 위험해졌을 것이다.

한 번에 한 변수만 바꾼 것이 여기서 값을 했다(C에서 두 개를 같이 넣어 원인을 못 가린 전례가 있다).

## 5. 진짜였던 것과 아니었던 것

분산을 알고 다시 보면 이렇게 갈린다.

**진짜 개선 (분산 범위 밖)**
- 원본 → A: macro 0% → 50%. A는 전 건이 단일 클래스라 분산 자체가 없었다.
- E: macro 100%, 분산 0%p. 3회 모두 동일.
- override 코드 게이트: 오탐 1건 → 0건. `"~할 수 있음"` 같은 재량 표현을
  금지 조항으로 오인하던 것을 문자열 검사로 차단했다. **코드 판정이라 흔들리지 않는다.**

**판정 불가 (분산 범위 안)**
- B vs C vs D의 우열 — 전부 노이즈였다

**설계 원칙이 재현성에서 먼저 값을 했다**

결정론적 코드로 만든 부분은 흔들리지 않고, LLM 판단에 의존하는 부분만 흔들렸다.

```
게이트(문자열 검사)   3회 모두 동일
절대금액 캡(코드 계산) 3회 모두 동일
금액·날짜 추출         94/94/94, 97/97/97
─────────────────────────────────────
LLM 판단(flag)        82/67/48   ← E 이전
```

「결정론 판단과 LLM 판단을 분리한다」는 원칙을 성능 때문에 세웠는데,
재현성 측면에서 먼저 효과가 나타났다.

## 6. 남은 문제

### ① 평가셋이 소진됐다 — 그리고 leakage 위험이 있다

macro 100%는 천장이다. **다음 수정의 효과를 측정할 수단이 없다.**

더 불편한 사실: 평가셋의 `지원불가` 정답 3건이 정확히 주유2 + 주차1인데,
E에서 taxonomy 목록에 **유류비와 주차비를 명시**했다. 정답을 알고 규칙을 쓴 것이므로
test set leakage에 가깝다.

목록에 함께 넣은 렌터카·범용기자재·귀금속은 **검증 0건**이다.

**확장 시도 → 불가 확정.** 보유 사진 142장을 조사한 결과:

```
142장 = 실제 영수증 105장 + scikit-image 샘플 이미지 37장
```

37장은 `.venv/site-packages/skimage/data/`의 `astronaut.png`, `coffee.png`, `moon.png` 등이었다
(조사 스크립트의 `build_index`가 가상환경을 제외하지 않은 버그. 세 스크립트 모두 수정함).
**안 본 영수증은 0장이었고, 렌터카·PC·귀금속 영수증은 애초에 없다.**

→ 이 한계는 추측이 아니라 확인된 사실이다. 평가셋 확장은 새 영수증 수집이 선행돼야 한다.

### ② 클래스 크기가 3이면 어떤 지표도 못 쓴다

`지원불가` 정답이 3건이라 **1건이 곧 33%p**다.
파이프라인이 완벽해도 이 클래스의 recall은 통계적으로 의미가 약하다.

### ③ 비영수증을 거절하지 않는다

조사 중 우연히 발견했다. 우주비행사 사진과 빈 그래프 이미지에 `확인필요` 판정을 냈다.

```
astronaut.png        → 확인필요
test_empty_graph.png → 확인필요
```

`extract` 단계에 "이 이미지가 영수증인가"를 묻는 곳이 없다.
파이프라인이 입력을 영수증이라고 **가정**하고 시작한다.
실서비스에서 사용자가 무관한 사진을 올리면 무엇이든 판정을 만들어낸다.

`flag=해당없음`이 아니라 **별도 거절 경로**가 필요하다
(`extract` 스키마에 `is_receipt: bool` 추가 → false면 즉시 반환).

### ④ `compliance_status`가 `flag`와 어긋난다

```
flag = 지원불가  →  compliance_status = 확인불가
```

컴플라이언스 Rule 0이 "flag가 지원불가면 위반의심으로"인데 지켜지지 않는다.
`status` 정확도 90%는 다수결 베이스라인과 동일해 **순이득 0**이다.

### ⑤ `flag=지원불가` 분기의 검색 쿼리가 회의비로 하드코딩돼 있다

```python
if flag == "지원불가":
    queries = ["회의비 현물성 물품 구매 지급 불가 불인정기준"]   # 고정
```

지원불가 사유가 회의비뿐이던 시절의 코드다. 주유소·주차장인데 회의비 조항을 검색한다.
E로 `지원불가` 판정이 늘면서 이 결함이 전면에 드러났다.

## 7. 측정 체계에 남긴 것

이번 일로 러너에 세 가지를 추가했다.

**① 단일 클래스 수렴 검사** — 다수결 베이스라인을 함께 출력한다.

```
**flag** 🚨 붕괴
- 모델 출력 종류 1개: `확인필요`×31
- 정확도 90% / 다수결 베이스라인 90% → 순이득 +0%p
```

A 이후의 90%를 성능으로 착각한 것이 이 지표를 만든 계기다.

**② macro recall** — 클래스 불균형에 눌리지 않는 값. 판정은 이것으로 한다.

**③ 건별 근거 목록** — `override 효과`, `게이트 차단`, `판정 근거(reasoning)`.
집계값이 같아도 구성이 다르면 여기서 드러난다.

**채택 기준**: 3회 최솟값이 이전 3회 최댓값을 넘을 때만 개선으로 인정한다.

## 9. 정정 및 후속 (2026-08-30 추가)

이후 `is_receipt` / `status` 작업 중 로그를 다시 판 결과, 위 본문 세 군데가 사실과 다르다.
본문은 당시 기록이므로 그대로 두고, 정정은 여기에만 적는다.

### ① override가 지원불가를 잡았다는 기록 — 현재 코드에서 재현 안 됨

§1의 `run1  override가 잡은 건: r001, r004`는 지금 코드로 3회 돌리면 **0건**이다.
r001/r002/r004 9/9 전부 게이트에 차단됐고(`flag_before_override`가 전부 `None`),
정답은 **분류 단계가 자력으로** 냈다. E(taxonomy 금지 목록)를 읽은 결과다.

지원불가 recall 3/3의 공로는 override가 아니라 taxonomy에 있다.

### ② "절대금액 캡은 코드 판정이라 안 흔들린다" — 틀렸다. 애초에 안 돈다

§5의 이 문장은 캡이 동작한다는 전제였는데, 캡은 구조적으로 죽어 있었다.

```
flag=지원불가 → sub_item="해당없음" 고정 (config.py:298)
ABSOLUTE_CAP_RULES 어디에도 "해당없음" 없음 → 항상 status="unknown"
게다가 반환값을 읽는 코드가 없다 (생성: pipeline.py:478 / 소비: 없음)
```

3회 동일했던 건 안정적이어서가 아니라 **매번 같은 unknown을 뱉어서**다.
