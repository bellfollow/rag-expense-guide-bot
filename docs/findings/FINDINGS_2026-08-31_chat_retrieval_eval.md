## 2. 결정적 사례 — q5

예비 관찰 10문항(라벨 없이 직접 작성해 `/search`로 관찰만 한 것) 중 하나:

> "노트북 사도 되나요?" → 정답 청크에 `노트북`이 리터럴로 박혀 있는데 top5 밖.

단어가 정답 청크에 그대로 있는데 못 찾는다 — 이건 어휘 격차(colloquial vs 규정용어)가 아니라 **구조 문제**라는 신호였다.

## 3. 국소화 — chunk4

```
기자재구입비                              1위  0.4943
기자재구입비 구매금지 품목                  1위  0.4671
범용성 기자재 노트북 PC 태블릿 구매 불가     2위  0.2803
노트북 사도 되나요?                        20위 0.1197
노트북                                    115위 0.0605
chunk4 자기 자신을 쿼리로                   1위  0.7984
```

자기 질의가 1위(0.7984)로 돌아온다 → **벡터는 멀쩡, 인덱싱 문제 아니다.**

원인: 세목 3개(④기자재구입비+⑤기자재임차비+⑥지식재산권창출활동비, 1376자)가 한 청크에 묶여 있어서, 그 안의 한 줄("구매금지 품목: 노트북, PC, 태블릿")이 청크 벡터의 지배 성분이 못 된다. 세목명("기자재구입비")으로 물으면 그 청크 전체의 주제와 맞아떨어져 1위가 나오지만, 리터럴 단어 하나("노트북")만 남기면 그 신호가 나머지 1300여 자(신청기한/계상비율/검수조서 등 절차규정)에 희석된다.

## 4. 헛짚음 — MIN_CHUNK_SIZE

병합 원인을 `MIN_CHUNK_SIZE=300`으로 보고 100으로 낮춰 재임베딩했다. **청크 15개 그대로, char_count 15개 전부 동일. 완전한 no-op.**

패킹 조건이 OR였다:

```python
if len(buffer) < min_chunk_size or len(buffer) + len(chunk) <= max_chunk_size:
    buffer += "\n\n" + chunk
```

이 문서는 **max 쪽이 실질 결정권을 쥔다** — 예를 들어 626(④)+254(⑤)+414(⑥) = 1294자로 이미 `MAX_CHUNK_SIZE`(1500) 이내라서, `min_chunk_size`를 300으로 두든 100으로 두든 두 번째 조건(`<= max_chunk_size`)만으로 병합이 성립한다. 첫 번째 조건(`min` 관련)은 애초에 이 문서에서 병합 여부를 가른 적이 없었다. **→ 조건문을 읽지 않고 상수 이름만 보고 짚었다.**

## 5. 문서별 분기 — 왜 guiideline.pdf에만 적용했나

```
guiideline.pdf        h3 15개, 135~1795자, taxonomy 15세목과 1:1
national_eval_rule    h3 204개, 11~22783자, 절반(104개)이 300자 미만
```

같은 규칙(h3 경계 강제분리)을 후자에 그대로 쓰면 11자짜리 청크가 104개 생기고, 22783자짜리 하나는 15조각 가까이 쪼개진다. 게다가 그 인덱스는 지금 이 순간 영수증 분류의 citation 9/9(유류비/주차비 조항 정확 인용)를 내고 있는 살아있는 인덱스다. **제외했다.**

구현: `chunk_by_markdown_heading`에 `split_at_level: int | None = None` 추가(기본값 None = 기존 동작 그대로), `select_and_chunk`가 이 값을 받아 전달, `pipeline.py`에서 `filename == "guiideline.pdf"`일 때만 `3`을 넘긴다. **11줄, 파일 2개**(`chunking.py`, `pipeline.py`).

## 6. 결과

```
              baseline   h3-split
hit@1 전체      55%   →   65%
colloquial      40%   →   60%
formal          70%   →   70%
MRR            0.639  →  0.758
미포함           4건   →   2건
```

**formal이 안 움직인 게 중요하다.** 세목명으로 묻는 질문(예: "전문가활용비 단기자문 지급 한도")은 원래도 잘 찾았고, 이번 수정이 겨냥한 건 세목명이 안 나오는 구어체 쪽이었다. 예상과 결과가 같은 방향으로 움직였다 — colloquial만 40%→60%로 크게 오르고 formal은 그대로.

회귀 없음: 영수증 macro recall 100%, status 100%(31장 1회), r001/r002/r004 citation 3/3 유지(유류비·유류비·주차비+일비 정확 인용). 국내여비 조항(유류비/렌터카/주차비)이 chunk22 하나에 통째로 남아있어서(⑤ 세목 하나만 분리됐을 뿐 세목 "안"은 안 쪼갰다) citation이 안 깨졌다.

## 7. `/search`는 결정론이다

3회 완전 동일 — jsonl 정렬 후 diff 0바이트, 소수점까지 일치. 임베딩(Jina)+코사인 검색(Qdrant)만 타는 경로라 반복 측정이 불필요하다는 게 실측으로 확인됐다.

단 `/chat` 전체(답변 생성까지 포함)는 Gemini 호출 단계가 있어 3회 원칙을 그대로 유지한다. **→ 이 프로젝트에서 "3회 반복"이 필요한 지점과 아닌 지점이 처음으로 갈렸다** — 결정론적 코드 경로(검색)와 LLM 판단 경로(답변/분류)를 구분해서 측정 비용을 아낄 수 있다는 뜻.

## 8. 라벨 설계에서 배운 것

gold를 `chunk_index`(숫자)로 잡았더니, 청킹 로직을 바꿔 재인덱싱하자마자 20문항 전부 매핑을 다시 해야 했다. 내용(note에 적어둔 근거 문장)을 새 청크 전문과 대조해 확정할 수 있었지만, **청크 번호는 재인덱싱마다 바뀐다는 걸 매핑 전엔 놓치고 있었다.**

→ 다음에 이런 라벨을 만든다면 gold를 근거 문장(또는 문장의 고유 부분문자열)으로 두고, `chunk_index`는 매 측정 시점에 그 문장을 포함한 청크를 찾아 계산하는 파생값으로 다뤄야 한다.
