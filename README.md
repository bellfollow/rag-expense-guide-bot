# 사업비 집행 가이드 챗봇

연구비(창업탐색비) 영수증을 넣으면 **집행 지침에 맞는지 판정하고 근거 조항을 인용**하는 RAG 시스템.

수십 페이지짜리 지침을 읽지 않고도 "이거 써도 되나"를 답하는 것이 목표다.

---

## 핵심 기능

| 기능 | 엔드포인트 | 상태 |
|---|---|---|
| 규정 질의응답(RAG) | `POST /chat` | 동작 |
| 영수증 비목분류 + 컴플라이언스 검토 | `POST /classify-receipt` | 동작 |
| 증빙서류 자동매칭 | `POST /classify-receipt` (`supporting_docs`) | 동작 |
| 정산보고서 일괄 검토 | `POST /review-settlement` | 동작 |
| 문서 법적 등급 자동분류 | (임베딩 파이프라인 내장) | 동작 |

## 실행 방법

**Windows(원클릭)**: `run_demo.bat` 더블클릭 — Docker Desktop이 꺼져있으면 자동 기동까지 하고, 컨테이너 기동 → 헬스체크 대기 → 브라우저 자동 오픈까지 한번에 처리한다. 끌 때는 `stop_demo.bat` 더블클릭(컨테이너+Docker Desktop+WSL까지 정지, 관리자 권한 필요·UAC 프롬프트 뜸).

**수동(macOS/Linux 또는 직접 제어하고 싶을 때)**:
```bash
docker compose up -d
# GET /health 로 준비 상태 확인 후 http://localhost:5000 접속
```

## 이 프로젝트에서 실제로 한 일

만든 것보다 **잰 것**이 핵심이다.

```
평가셋 31장 직접 구축 → 측정 → 직관과 반대인 결과 발견
      → 측정 자체를 의심 → 원인 규명 → 수정 → 재측정
```

### 결과 (영수증 31장, 3회 반복 측정)

| 지표 | 수정 전 | 수정 후 |
|---|---|---|
| **macro recall** | **0%** | **100%** |
| 3회 반복 분산 | 34%p | **0%p** |
| 지원불가 recall | 0/3 | **3/3** |
| 확인필요 recall | 0/28 | **28/28** |
| 과신율 | 100% | **0%** |
| 금액 추출 | 94% | 94% |
| 날짜 추출 | 97% | 97% |

`flag` 전체 정확도(94% → 100%) 대신 **macro recall**로 보고한다.
정답 분포가 `확인필요` 28 / `지원불가` 3이라, 전체 정확도는 다수 클래스에 눌려
"확인필요만 찍는 모델"도 90%를 받기 때문이다.

## 1. 발견: 판정이 거꾸로였다

첫 측정에서 `flag` 정확도가 **0%**였다. 그런데 틀린 방향이 둘로 갈렸다.

```
애매한 식비 26건    →  "지원불가"로 단정      (자신있게 거절)
명백한 위반 3건     →  "확인필요"로 유보      (판단 회피)
```

주유비(85,000원)와 주차비(13,500원)는 지침에 **명시적으로 지급 불가**라고 적혀 있다.

> L248 — "자가 이용 시 동일구간 내 대중교통비 정액을 기준으로 집행한다.
> **유류비는 지원되지 않으며**, 이 때 톨비 영수증을 제출하여야 한다."
>
> L258 — "출장지 내에서 소요되는 교통비, **주차비 등은 일비에 포함되므로 별도로 청구할 수 없다.**"

시스템은 이 셋을 전부 놓쳤고, 반대로 판단 근거가 없는 식당 영수증은 확신을 갖고 거절했다.

판정 근거를 열어보니 논리가 일관됐다.

```
"출장 증빙이 없어 → 회의 목적 식비로 간주 → 지원 불가"
```

**"증빙이 없다"를 "확인필요"가 아니라 "회의비로 간주"로 처리**하고 있었다.
정보 부족을 불리한 추정으로 메우면서 `confidence`는 전부 `high`였다.

---

## 2. 함정: 90%가 성능이 아니었다

분류 프롬프트에 "정보 부족 → 확인필요" 규칙을 넣자 정확도가 **0% → 90%**로 뛰었다.

성능이 아니었다.

```
모델 출력 종류 1개: `확인필요` × 31
정확도 90% / 다수결 베이스라인 90% → 순이득 +0%p
```

31건 **전부**를 `확인필요`로 냈다. 과잉 거절이 과잉 유보로 바뀐 것뿐이고,
방향만 뒤집힌 동일한 실패였다.

이 경험으로 채점기에 **단일 클래스 수렴 검사**를 넣었다. 이후 모든 측정은
다수결 베이스라인을 함께 출력하고, 개선 여부는 **순이득(%p)**으로 판단한다.

---

## 3. 더 큰 함정: 1회 측정은 측정이 아니었다

네 번 수정하고 각각 **1회씩** 측정해 개선/악화를 판정했다.

| 수정 | macro | 그때의 판정 |
|---|---|---|
| B | 82% | 성공 |
| C | 67% | 순손실, 롤백 |
| D | 67% | 회복 실패, 원인 불명 |

D에서 설명되지 않는 일이 있었다. C에서 성공했던 사례가 실패하고 **다른 사례가 대신 성공**했다.
코드 변경으로는 설명되지 않았다.

코드를 한 글자도 바꾸지 않고 3번 돌렸다.

```
run1  macro 82%
run2  macro 67%
run3  macro 48%      ← 동일 코드, 동일 입력, temperature=0
```

**분산 34%p. B·C·D가 전부 이 범위 안에 있었다.**
네 번의 판정 중 무엇에도 근거가 없었다.

집계값(67% → 67%)만 봤다면 "변화 없음"으로 넘어갔을 것이다.
채점기가 **건별 판정 근거를 함께 출력**하고 있었기에 구성 변화가 보였다.

> 집계값이 같아도 구성이 다르면 의심해야 한다.

## 4. 원인: 흔들림은 정보 부족의 증상이었다

추측을 멈추고 같은 이미지를 3번씩 태워 **단계별 출력의 동일성**을 비교했다(9콜, 약 3원).

```
① 추출  vendor "성수주유소"  item "휘발유 주유"  amount 85000  date 2026-08-03
        ↓ 네 값 모두 3회 완전히 동일
② 분류  flag "확인필요" / "지원불가"     🚨 갈림
② 분류  confidence "low"                 (모델도 자기가 모른다는 걸 안다)
```

입력이 글자 하나 다르지 않은데 분류가 갈렸다.

안 흔들리는 것과 흔들리는 것을 나란히 놓으면 답이 보인다.

```
안 흔들림   금액, 날짜        영수증에 답이 인쇄돼 있다
흔들림      비목, 지원가부     영수증에도 분류 목록에도 답이 없다
```

주유비 금지 근거는 가이드라인에만 있는데, 분류 단계는 RAG를 쓰지 않고
고정 비목 목록만 본다. 모델은 답을 모르니 비슷한 확률의 후보 사이에서 매번 다르게 찍었다.

**`temperature=0`으로 막을 수 없다. 정보를 줘야 한다.**

## 5. 수정: 금지 조항을 "판정 가능 여부"로 갈라 제공

분류 단계에 **RAG를 붙이지 않았다.** 고치려는 것이 불안정성인데
검색을 추가하면 불안정 요인이 하나 더 늘기 때문이다. 고정 목록에 텍스트로만 넣었다.

```
[영수증만으로 판정 가능 → 지원불가로 판정]
  유류비 · 주차비 · 렌터카 · 출장지 내 택시 · 범용성 기자재(PC/노트북) · 귀금속

[영수증만으로 판정 불가 → 확인필요로 유보]
  회의비 · 협약기간 밖 집행 · 친족 간 거래
```

지금까지 이 둘이 섞여 있어서, 모델은 회의비 조항 하나로 모든 식당을 거절하거나
명백한 유류비를 판단 유보로 미뤘다.

### 결과

```
수정 전   flag: "확인필요" / "지원불가"   🚨    confidence: low
수정 후   flag: "지원불가"                고정   confidence: high
```

`confidence`가 `low → high`로 바뀐 것이 결정적이다.
모델이 근거를 갖게 되어 확신하는 것이고, 이전에는 몰라서 동전을 던지고 있었다.

31장 3회 재측정: **macro recall 100% / 100% / 100%, 분산 0%p.**

부수 확인: 추출 단계의 `vendor`·`item`은 여전히 실행마다 표기가 흔들리는데
(`"(유)풍차주소"` ↔ `"(유)풍차주유소"`), **판정은 고정됐다.**
분류가 근거를 갖게 되니 표기 차이에 둔감해졌고, 추출 프롬프트는 건드릴 필요가 없었다.

## 6. 측정 도구 자체의 버그

첫 측정에서 컴플라이언스 정확도가 0%로 나왔다. 모델 성능이 아니라
채점기가 존재하지 않는 필드를 읽고 있었다.

```python
# 채점기가 읽던 것
d["compliance"].get("status")            → 항상 None

# 파이프라인 실제 스키마
{"compliance_status": "준수|위반의심|확인불가", ...}
```

필드명도 값 어휘도 달랐다.
**0%라는 숫자를 그대로 믿었으면 존재하지 않는 문제를 고치고 있었을 것이다.**

## 7. OCR vs Vision — 선택 근거

같은 영수증 100장을 로컬 OCR(EasyOCR)과 Vision LLM(Gemini)으로 처리해 비교했다.

| | EasyOCR + 규칙 파싱 | Gemini Vision |
|---|---|---|
| 금액 (교차검증 4건) | **0/4** | **4/4** |
| 날짜 | 73/100 | 30/31 (97%) |
| 카드사명 인식 | **4/82 (5%)** | — |

EasyOCR은 `11,950`을 `71,950`으로, `롯데`를 `못데`·`로데`·`룻데`로 읽었다.
같은 카드로 82번 결제했는데 정확히 읽은 것은 4번뿐이다.

**정규식을 보강해도 소용없다** — 입력이 이미 깨져 있어 천장이 걸려 있다.
후처리 규칙을 늘리는 것은 OCR 성능이 아니라 규칙 작성자의 노력을 측정하는 일이 된다.

한글 열전사 영수증에서는 문자 인식과 의미 해석을 분리하지 않는 편이 낫다는 결론.

## 8. 검색 품질 개선 (4라운드)

`required_documents`(필요 증빙서류)가 엉뚱한 조항을 인용하는 문제를 4라운드에 걸쳐 추적.

| | 개선 전 | 개선 후 |
|---|---|---|
| 참고1(제출서류 표) top5 진입 | 4/6 | **6/6** |
| 참고2(불인정 기준) 오염 | 4/6 | **1/6** |
| 국내여비 쿼리 순위 | 4위 | **2위** |
| 소모품비 쿼리 순위 | 10위 | **1위** |

**틀린 진단 3번을 거친 끝에 찾은 실제 원인**: 하나의 쿼리에 서로 다른 목적
(한도 확인 / 서류 확인)을 섞어 넣고 있었다.

```python
# 개선 전 — 한 쿼리에 목적 3개
f"{main_category} {sub_item} 사용기준 제출서류 불인정기준"

# 개선 후 — 목적당 쿼리 1개, 결과 병합
[f"{sub_item} 한도 사용기준", f"{sub_item} 제출서류"]
```

중간에 시도한 수정 하나는 국내여비 순위를 4위에서 19위로 **악화**시켰다.
측정 없이 진행했다면 개선으로 착각했을 변경이다.

## 9. 아키텍처

```
영수증 이미지
   │
   ├─ ① 추출        Gemini Vision → {상호, 금액, 날짜, 품목}
   │
   ├─ ② 비목 분류    고정 taxonomy 15개 + 금지 조항 목록 (RAG 없음)
   │                 → {main_category, sub_item, flag}
   │
   ├─ ③ 컴플라이언스  jina-embeddings-v3(1024d) → Qdrant(COSINE) → Gemini
   │                 → {판정, 인용 조항, 필요서류}
   │
   └─ ④ 증빙 매칭    필요서류 ↔ 첨부서류 대조
```

**결정론 / LLM 판단 분리** — 금액 한도 검사는 코드가 계산하고 LLM에게 묻지 않는다.
컴플라이언스가 "금지 조항을 찾았다"며 판정을 뒤집으려 할 때도,
인용문에 실제 금지 표현(`"지급하지 아니한다"`, `"청구할 수 없다"` 등)이 있는지를
**문자열 검사로 게이트**한다. LLM이 제출서류 표를 금지 조항으로 오인한 사례가 있었고,
그 오탐 1건이 이 게이트로 0건이 됐다.

이 원칙은 성능보다 **재현성**에서 먼저 값을 했다.

```
게이트(문자열 검사)     3회 모두 동일
절대금액 캡(코드 계산)   3회 모두 동일
LLM 판단(수정 전)       82% / 67% / 48%
```

**문서 법적 위계(doc_tier)** — 법률(1) → 시행령 → 시행규칙 → 매뉴얼 → 고시/훈령 → 사업지침(6).
지침과 상위 법령이 충돌하면 상위 강행규정을 우선하고, 어느 쪽을 택했는지 근거를 남긴다.

**보수적 판정** — 등급·맥락 정보가 없으면 가장 관대한 한도를 적용한다.
거짓 양성(정상을 위반으로 판정)을 내지 않는 것이 우선이다.

## 10. 평가셋

영수증 105장 → 중복 제거 100장 → **31장 선별**.

무작위로 뽑지 않았다. 전부 식비면 "무조건 식비"라고 찍는 모델이 만점을 받는다.

| 태그 | 수 | 역할 |
|---|---|---|
| 지원불가 확정 (주유2·주차1) | 3 | 명시적 금지 조항 |
| 숙박 상한초과 (모텔 520,000원) | 1 | 지역별 상한 |
| 현물성물품 후보 (편의점) | 3 | 회의비 조항 |
| 다인분 회의비 후보 | 4 | 인분수 판별 |
| 출장중 식비 (익산 클러스터) | 8 | 날짜·지역이 뭉친 실제 출장 |
| 일상 식비 | 8 | 60장 중 8장만 — 다수 클래스 억제 |
| 카페 | 4 | 회의/개인 경계 |

정답의 다수는 `확인필요`다. 영수증만으로 회의 식사인지 출장 식사인지 사람도 구분할 수 없다.
**이 셋이 재는 것은 정확도가 아니라 "모를 때 모른다고 하는가"**이며,
실제 정산에서 반려율을 좌우하는 것도 그쪽이다.

## 11. 한계

**평가셋이 소진됐다.** macro 100%는 천장이고, 다음 수정의 효과를 측정할 수단이 없다.

**leakage 위험이 있다.** `지원불가` 정답 3건이 정확히 주유2 + 주차1인데,
수정에서 금지 조항 목록에 유류비와 주차비를 명시했다. 정답을 알고 규칙을 쓴 셈이다.
함께 넣은 렌터카·범용기자재·귀금속은 **검증 0건**이다.

**확장은 불가능한 것으로 확인됐다.** 보유 사진 142장을 조사한 결과
실제 영수증 105장 + 라이브러리 샘플 이미지 37장이었다. 안 본 영수증은 0장이고,
해당 유형 영수증은 애초에 없다. 평가셋 확장은 새 영수증 수집이 선행돼야 한다.

**클래스 크기가 3이면 지표가 약하다.** `지원불가` 정답이 3건이라 1건이 곧 33%p다.

**비영수증을 거절하지 않는다.** 조사 중 우연히 확인했다 —
우주비행사 사진과 빈 그래프 이미지에 `확인필요` 판정을 냈다.
`extract` 단계에 "이 이미지가 영수증인가"를 묻는 곳이 없어,
파이프라인이 입력을 영수증이라고 가정하고 시작한다.

**`compliance_status`가 `flag`와 어긋난다.** `flag=지원불가`인데 `확인불가`가 나온다.
`status` 정확도 90%는 다수결 베이스라인과 같아 순이득이 0이다.

**31장은 통계적으로 작다.** 신뢰구간 ±18%p.

**결제수단이 정답과 상관돼 있다.** 31장 전부 법인카드다.
`개인카드 × 인정가능` 조합이 비어 있어, 모델이 결제수단을 지름길로 쓸 여지가 남아 있다.

## 12. 스택

`FastAPI` · `Gemini 3.5 Flash Lite` · `jina-embeddings-v3` · `Qdrant` · `MongoDB` · `Docker`

초기 프로토타입은 n8n 오케스트레이션 + 변환 서버 분리 구조였으나(`backup/docker-compose.yml`),

현재 구성은 `mongodb` · `qdrant` · `fastapi` 세 컨테이너다.

## 13. 측정 도구

`eval/` 아래에 채점기와 진단 도구가 있다. 실물 영수증 이미지는 커밋하지 않는다.

| 파일 | 역할 |
|---|---|
| `eval/run_eval.py` | 평가셋 채점. 다수결 베이스라인 · macro recall · 건별 판정 근거 출력 |
| `eval/variance_probe.py` | 같은 이미지를 N회 태워 **단계별 동일성** 비교. 분산이 어느 단계에서 시작하는지 국소화 |
| `eval/survey_all.py` | 미검토 사진을 태워 분포만 확인 (평가셋 확장 여지 판정용) |
| `eval/labels_prefilled.csv` | 31장 정답 라벨 |

```bash
python eval/run_eval.py --api http://localhost:5000 --images <영수증 폴더>
```

사용법은 `eval/README.md` 참조.

**채택 기준**: 3회 최솟값이 이전 3회 최댓값을 넘을 때만 개선으로 인정한다.
