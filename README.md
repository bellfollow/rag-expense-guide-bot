# AI 연구비 집행 컴플라이언스 챗봇

국가연구개발혁신법·사업 운영지침 기반으로 연구비 집행 질의응답과 영수증 비목분류/컴플라이언스 검토를 자동화하는 RAG 시스템.

## 문제 정의

연구비를 다뤄본 사람이면 다 아는 문제: 규정집은 두껍고(500p+), 사업마다 별도 지침이 또 있고, 담당자는 영수증 한 장 처리할 때마다 "이거 이 비목 맞나, 한도는 안 넘었나, 서류는 다 챙겼나"를 매번 손으로 대조한다. 규정을 잘못 해석해서 안내하면 그게 바로 사고로 이어지는 도메인이라, 일반적인 "그럴듯하게 답하는 챗봇"은 오히려 위험하다. 이 프로젝트는 두 가지를 목표로 한다:

1. **문서 근거 없인 답하지 않는 RAG 챗봇** — 근거가 약하면 약하다고 말한다.
2. **영수증 한 장에서 비목분류 + 컴플라이언스 위반여부까지 자동 판정** — 사람이 규정집 대조하던 작업을 대체.

## 핵심 기능

| 기능 | 엔드포인트 | 상태 |
|---|---|---|
| 규정 질의응답(RAG) | `POST /chat` | 동작 |
| 영수증 비목분류 + 컴플라이언스 검토 | `POST /classify-receipt` | 동작 |
| 문서 법적 등급 자동분류 | (임베딩 파이프라인 내장) | 동작 |
| 정산보고서 일괄 검토(서류 컴플라이언스) | `POST /review-settlement` | 설계 완료, 구현 예정 |

## 아키텍처

```
PDF 규정집 ──▶ Gemini 변환(Markdown) ──▶ 문서 등급 자동분류 ──▶ 청킹 ──▶ Jina 임베딩 ──▶ Qdrant
                                                                                      │
사용자 질문 ──▶ Jina 임베딩(query) ──▶ Qdrant 검색(top-k) ──────────────────────────┘
                                              │
                                              ▼
                                    Gemini(문서 근거만 사용) ──▶ 답변 + 출처 + 신뢰도

영수증 이미지 ──▶ Gemini Vision 추출 ──▶ 고정목록 비목분류 ──▶ 비목명 재검색(RAG) ──▶ 컴플라이언스 판정
```

**스택**: FastAPI · Qdrant(벡터DB) · MongoDB(예비, 현재 미사용) · Gemini(변환/분류/답변) · Jina Embeddings v3

## 의사결정 서사

### 1. "생략하지 마라"고 시켰는데 생략하는 모델

지침 문서(`guiideline.pdf`, 30p) 변환 결과를 다시 열어봤더니 부록 섹션이 이렇게 나와 있었다.

```
# Ⅴ. 관련서식
(별지 제1호 ~ 제15호 서식 생략)

## 참고 1. 창업탐색비 집행관련 제출서류
(표 생략)

## 참고 2. 창업탐색비 불인정 기준
(표 생략)
```

시스템 프롬프트엔 이미 "표를 생략하지 말라"는 지시가 있었다. 그런데도 모델이 "부록은 안 중요하다"고 임의 판단해서 통째로 스킵한 것이다. 원본 PDF를 직접 열어 텍스트 추출을 확인해보니 스캔본이 아니라 텍스트가 멀쩡히 있었다 — 즉 변환이 불가능해서가 아니라 모델이 알아서 생략한 것.

이 부록엔 하필 이 프로젝트에서 제일 중요한 데이터가 들어있었다: 비목별로 어떤 서류를 사전/사후에 제출해야 하는지 정리한 표, 그리고 비목별 불인정(지원불가) 판정 기준표. 재변환해서 이 표들을 복구하고 나서야 비목분류 결과에 "이 지출은 왜 안 되는지"에 대한 실제 근거를 붙일 수 있게 됐다.

이건 사실 새로운 버그가 아니라 이전에 516p짜리 상위법 문서에서도 겪었던 것과 같은 패턴이다 — 파일 크기와 무관하게, 반복적/양식적으로 보이는 콘텐츠는 모델이 스스로 요약 대상이라고 오판하는 경향이 있다. 그래서 이제는 "변환됐다"와 "빠짐없이 변환됐다"를 별개로 취급하고, 신규 문서를 넣을 때마다 "(생략)" 같은 placeholder 문자열이 남아있는지 확인하는 걸 기본 루틴으로 삼는다.

### 2. 문서 등급을 사람이 정해줄 것인가, 모델이 판단하게 할 것인가

이 시스템은 상위법(국가연구개발혁신법)과 특정 사업의 운영지침을 동시에 참조한다. 두 문서가 같은 사안에 다른 기준을 제시하면 어느 쪽을 우선할지 판단 근거가 필요하다.

처음엔 "파일명 → 등급"을 코드에 직접 매핑해두는 방식으로 시작했다. 문서가 2개뿐일 때는 문제없었지만, 이 방식은 새 문서가 추가될 때마다 사람이 매번 등급을 손으로 등록해줘야 한다는 근본적 한계가 있었다. 확장성이 없는 설계였다.

그래서 문서 내용을 직접 읽고 법적 위계(법률 > 시행령 > 시행규칙 > 법령해설_매뉴얼 > 고시·훈령·예규 > 사업지침·운영요강)를 자동으로 판정하는 모델을 파이프라인에 넣는 쪽으로 바꿨다. 첫 시도에서는 판정 기준을 "문서 형식"(제목에 "매뉴얼"이 들어가면 지침류로 취급)으로 잡았더니, 실제로는 상위법 전체를 해설하는 문서인데 제목이 "OO법 매뉴얼"이라는 이유만으로 사업지침과 같은 등급으로 잘못 분류되는 문제가 나왔다. 형식이 아니라 "이 문서가 특정 사업 하나에만 적용되는가, 아니면 제도 전체에 적용되는가"라는 적용 범위 기준으로 바꾸고 나서야 두 문서가 의도한 대로 갈라졌다.

지금은 신규 문서를 넣으면 사람 개입 없이 등급이 자동으로 붙는다. 다만 이 로직이 실제 "상위법과 지침이 정면으로 충돌하는" 사례에서 검증된 적은 아직 없다 — 지금까지는 두 문서가 같이 검색돼도 실제 상충 없이 지침이 자연스럽게 우선 채택되는 경우만 확인했다.

## 실행 방법

**Windows(원클릭)**: `run_demo.bat` 더블클릭 — Docker Desktop이 꺼져있으면 자동 기동까지 하고, 컨테이너 기동 → 헬스체크 대기 → 브라우저 자동 오픈까지 한번에 처리한다. 끌 때는 `stop_demo.bat` 더블클릭(컨테이너+Docker Desktop+WSL까지 정지, 관리자 권한 필요·UAC 프롬프트 뜸).

**수동(macOS/Linux 또는 직접 제어하고 싶을 때)**:
```bash
docker compose up -d
# GET /health 로 준비 상태 확인 후 http://localhost:5000 접속
```
