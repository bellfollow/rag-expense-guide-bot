# FINDINGS — required_documents 부정확 원인 규명: 4라운드에 걸친 원인 이동 (2026-08-23)

> 태그: 컴플라이언스 RAG 검색 개선
> 결과: 해결. `국내여비` 2위 / `소모품비` 1위 (둘 다 이전엔 top5 밖)
> 관련: `docs/document_match.md`, `DEV_LOG.md`

---

## 0. 한 줄 결론

`required_documents`가 부정확했던 진짜 원인은 **검색 쿼리 하나에 목적이 다른 두 질문이
섞여 들어간 것**이었다. 검색 랭킹도, 문서 등급도, 청킹도 아니었다.

원인 후보가 네 번 이동했고, **앞선 세 번은 전부 "코드에서 이상한 것을 보고
즉시 원인으로 건너뛴" 것**이었다. 네 번째만 실측이 직접 가리켰다.

---

## 1. 증상

`/classify-receipt`의 3단계(컴플라이언스)가 반환하는 `required_documents`가
비목에 따라 부정확했다. 사업지침의 `[별지N]` 특화 서식 대신 상위 문서의
일반 증빙 목록이 나오는 경우가 있었고, **같은 코드인데 실행 시점에 따라 결과가
달랐다**(2026-08-16 vs 08-19).

착수 시점 증상: `hierarchy_note`가 거의 발동하지 않았다. 발동 조건은 상위법과
지침이 동시에 검색 컨텍스트에 들어오는 것인데, 그게 안 됐다.

## 2. 원인 후보의 이동 — 네 번

### 라운드 1 — "doc_tier가 검색에 반영 안 됨" — 반증

**가설의 근거**: 코드를 읽고 발견한 사실.

```python
# embeddings.py
def search(query_vector, top_k=5):
    return qdrant_client.search(..., limit=top_k)   # 순수 코사인
```

`config.py`에 문서 등급 체계 6단계(`doc_tier_rank`)를 구축해두고, Qdrant payload에
`doc_tier_rank`까지 저장해두고, **검색 랭킹에는 안 쓰고 프롬프트에만 썼다.**

"그래서 사업지침이 상위 문서에 밀리는구나" — tier 쿼터 도입을 설계했다.

**실측 결과 — 가설이 반증됨.**

| 쿼리 | rank6(사업지침) 비율 | 서로 다른 rank |
|---|---|---|
| 기자재구입비 | 2/5 | 2종 |
| 외주용역비 | 4/5 | 2종 |
| 교육비 | 2/5 | 2종 |
| 소모품비 | **5/5** | 1종(독점) |
| 국내여비 | 4/5 | 2종 |
| 창업탐색추진비 | **5/5** | 1종(독점) |
| 지원불가 고정쿼리 | 2/5 | 2종 |

사업지침이 top_k에 0개인 쿼리: **0/7**. 반대기미커녕 2개 쿼리에서 top5를 독점했다.
score 분포는 guiideline(0.42~0.73)이 national_eval_rule(0.44~0.55)보다 상단 우위.

`hierarchy_note` 발동 조건(2종 이상 rank 공존)은 7개 중 5개에서 이미 충족돼 있었다.

**걱정 방향이 반대였다.** 지침이 밀리는 게 아니라 오히려 독점하고 있었다.

> 여기서 tier 쿼터를 구현했다면, 이미 잘 되는 걸 "고치고" 대신
> 증상이 남는 걸 보며 다시 원인을 못 찾았을 것이다.

### 라운드 2 — "표가 청크 경계에서 잘림" — 고쳤으나 회귀

같은 진단에서 진짜 버그가 잡혔다.

`chunking.py:198`의 강제 문자수 슬라이스가 "참고 1. 창업탐색비 집행관련 제출서류"
표를 행 한가운데서 잘랐다. `required_documents`가 참조해야 할 바로 그 표였다.

```
chunk13  char_count=1500  → MAX_CHUNK_SIZE와 정확히 일치
chunk14  char_count=233   → 헤더 없이 "청 서류 |"로 시작
                             국내여비/문헌구입비/일반수수료 row + [별지14][별지11]
```

**왜 비목별로 결과가 갈렸는지 설명됨**:

```
"국내여비" 쿼리 → chunk14 안에 그 단어가 있음 → 4위(top5 안)
"소모품비" 쿼리 → 그 단어는 chunk13에 있음      → chunk14는 10위(top5 밖)
```

표가 잘린 위치에 따라 비목별로 운이 갈렸다.

**수정**: 마크다운 표를 감지해 청크 경계로 자르지 않음(통짜 emit).
`TABLE_MAX` 상한과 초과 시 경고 로그를 함께 넣었다.

**결과 — 부분 성공, 부분 회귀**:

| 지표 | before | after |
|---|---|---|
| 표 분할 | 2조각 | **1개** ✓ |
| breadcrumb 프리픽스 | 없음 | **자동 복원** ✓ |
| 소모품비 | 10위 | **4위** ✓ |
| 국내여비 | 4위 | **19위** ✗ |

**국내여비가 회귀했다.** 233자 조각은 3개 비목만 담아서 그 비목들의 벡터가
집중돼 있었는데, 1733자 통짜가 되니 15개 비목이 섞여 임베딩이 희석됐다.

> `TABLE_MAX` 주석에 "너무 긴 청크는 임베딩 특정성이 떨어진다"고 직접 적어둔
> 우려가 이 케이스에서 실제로 발현됐다.

### 라운드 3 — "행 단위 분할 + 헤더 반복" — 더 악화

라운드 2의 데이터가 "짧고 주제가 좁은 청크가 그 주제 쿼리에 강하다"를 보여줬으므로,
그걸 우연이 아니라 설계로 만들기로 했다. 각 데이터 행마다 헤더를 반복해 붙여
1청크로 만들었다.

**결과 — 양쪽 다 실패**:

| 지표 | original | 통짜 | 행분할 |
|---|---|---|---|
| 국내여비 | 4위 | 19위 | 10위 |
| 소모품비 | 10위 | 4위 | 7위 |

둘 다 top5 밖. 통짜보다도 나빴다.

그리고 **새 독점**이 생겼다. 7개 쿼리 중 5개에서 `참고 2` 표 조각이 top5를
3칸 이상 점유했고, `창업탐색추진비`는 top5가 전부 그 표 조각이었다.
청크 수는 15 → 24로 늘었다.

**여기서 진짜 원인이 드러났다.**

```
쿼리 접미사:  "...사용기준 제출서류 불인정기준"
표 헤더:      "참고 2. 창업탐색비 불인정 기준 | 구분 | 제출서류 |"
                            ^^^^^^^^^          ^^^^^^^^
```

행마다 헤더를 반복하는 **"쿼리와 리터럴로 겹치는 문구를 가진 조각"이 1개에서
11개로 늘었다.** 표 내용이 어떤 비목이든 상관없이 헤더만으로 점수를 받았다.

행분할이 이 문제를 만든 게 아니라, **원래 있던 문제를 증폭시켜 드러냈다.**

### 라운드 4 — "쿼리가 목적 두 개를 한 문장에 넣음" — 진짜 원인

```python
search_query = f"{main_category} {sub_item} 사용기준 제출서류 불인정기준"
```

이 한 줄에 서로 다른 세 가지 질문이 들어 있었다:

```
"이 비목의 한도·사용기준이 뭔가"    → 집행기준 조항을 찾아야 함
"이 비목의 필요한 제출서류가 뭔가"   → 참고 1 표를 찾아야 함
"불인정 기준이 뭔가"                → 참고 2 표를 찾아야 함
```

**세 목적을 한 벡터로 만들면 이 중 어느 것도 정확히 못 찾는다.** 그리고 각 목적의
키워드가 다른 목적의 문서 제목과 리터럴로 겹쳐서, 서로를 부당하게 띄워올렸다.

**검증 — 코드 수정 없이 스크립트로 3개 조합 비교**:

| 비목 | (A) 현재 참고1/참고2 | (B) 접미사 제거 | (C) 목적 분리 |
|---|---|---|---|
| 기자재구입비 | 없음 / 없음 | 없음 / 없음 | **4위** / 없음 |
| 외주용역비 | 3위 / 2위 | 없음 / 없음 | **5위** / 없음 |
| 교육비 | 3위 / **1위** | 없음 / 없음 | **4위** / 없음 |
| 소모품비 | 4위 / 2위 | 없음 / 없음 | **4위** / 없음 |
| 국내여비 | 없음 / 2위 | 없음 / 없음 | **4위** / 없음 |
| 창업탐색추진비 | 3위 / **1위** | 없음 / 없음 | **4위** / 3위 |

- **(B) 접미사 완전 제거는 해결책이 아니다.** 참고2 오염은 사라지지만
  참고1도 같이 사라진다. 참고1 제목이 실제로 "...제출서류"라 그 단어와는
  진짜 연관이 있는 매치였다. "둘 다 지워버리는" 것.
- **(C) 목적 분리가 답이다.** 참고1은 안정적으로 들어오고(5/6), 참고2 오염은
  1/6로 줄어든다.

## 3. 최종 수정

```python
if flag == "지원불가":
    # 지급 대상이 아니므로 required_documents는 빈 배열이 정상.
    # "제출서류"를 빼고 불인정 근거만 찾는다.
    queries = ["회의비 현물성 물품 구매 지급 불가 불인정기준"]
else:
    queries = [
        f"{sub_item} 한도 사용기준",   # 집행기준 조항
        f"{sub_item} 제출서류",        # 참고 1 표
    ]

per_query_k = -(-top_k // len(queries)) + 1   # 올림 나눗셈
# 각 쿼리로 검색 → point id 기준 dedup(최고 score 유지) → score 내림차순 top_k
```

**청킹은 통짜 상태로 유지**(라운드 2의 표 절단 방지는 살리고, 라운드 3의 행분할은
되돌림). **재임베딩 불필요** — 쿼리만 바뀌므로 인덱스를 안 건드린다.

### 결과

| 지표 | original(표절단) | 통짜 | 행분할 | **최종** |
|---|---|---|---|---|
| 참고1 top5 진입 | 미측정 | 4/6 | 1/6 | **6/6** |
| 참고2 오염 | 미측정 | 4/6 | 7/7 | **1/6** |
| 국내여비 | 4위 | 19위 | 10위 | **2위** |
| 소모품비 | 10위 | 4위 | 7위 | **1위** |
| rank 2종 공존 | 5/7 (71%) | — | — | **5/6 (83%)** |
| 컨텍스트 문자수 | 6058~7430 | — | — | 5742~7142 |

**국내여비와 소모품비가 동시에 top5에 들어온 게 이번이 처음이다.**
`hierarchy_note` 발동 조건도 baseline 대비 떨어지지 않았다(오히려 소폭 상승).
컨텍스트 크기와 비용은 baseline과 비슷했다.

### 구현 중 잡힌 이슈 하나

스크립트 측정과 실제 파이프라인이 지원불가 케이스에서 갈렸다.
초기 구현에서 `per_query_k = top_k//2 + 1`을 단일 쿼리에도 적용해 컨텍스트가
5개 → 3개로 줄었다. 판정 순위엔 영향 없었다(참고2가 여전히 1위,
`required_documents`는 빈 배열이 정상). 그러나 **"우연히 괜찮다"와 "설계가 맞다"는
다르므로** 위 올림 나눗셈 공식으로 교체했다. 쿼리 개수(1개 또는 2개)에 따라
자동으로 스케일하므로 두 분기 모두 같은 공식으로 top_k를 채운다.

## 4. 무엇을 배웠나

### 4-1. 세 번의 오진이 전부 같은 패턴이었다

```
라운드 1  코드의 doc_tier가 안 쓰임을 봄       → "그래서 지침이 밀린다"
라운드 2  표가 잘린 걸 봄                       → "그래서 못 찾는다"
라운드 3  짧은 조각이 특정 쿼리에 강한 걸 봄     → "그러니 잘게 쪼개자"
```

전부 **"코드에서 이상한 것"을 보고 "그래서 이 증상이 된다"로 건너뛴 것**이었다.
관찰과 증상 사이의 인과를 확인하지 않았다.

라운드 2는 실제 버그였지만(표는 진짜 잘려 있었다) **그게 이 증상을 주는 원인은
아니었다.** 진짜 버그를 찾았다는 것과 그것이 원인이라는 것은 다르다.

### 4-2. 매 라운드 before/after를 남긴 게 결정적이었다

`original / 통짜 / 행분할 / 최종` 4자 대조가 없었다면:

- 라운드 2에서 소모품비 개선만 보고 "성공"으로 넘어갔을 것(국내여비 회귀를 못 봄)
- 라운드 3이 같은 실수인지 확인 불가
- 라운드 4에서 "정말 나아진 건가"를 증명 못 함

**측정 없이 고치면 고쳤는지도 모른다.**

### 4-3. 성공 기준의 착시를 조심해야 했다

라운드 3 착수 전 이렇게 정해뒀다:

> `[1]`과 `[2]`가 **동시에** top5 안에 들어와야 성공이다.
> 하나만 되면 트레이드오프가 이동한 것뿐이지 해결이 아니다.
> 그 경우 실패로 보고하고 원인을 분석하라 — 성공으로 포장하지 마라.

이 문장이 없었으면 라운드 3을 "국내여비 19→10위 개선"만 보고 성공으로
보고했을 수 있다. 실제로는 소모품비가 4→7위로 같이 나빠졌었다.

### 4-4. 인덱스를 안 건드리는 실험이 훨씬 쌌다

라운드 1~3은 매번 청킹 수정 → 재청킹 → 재임베딩 → 재측정이었다.
라운드 4는 **쿼리만 바꾸므로 검색만 다시 돌리면 됐다.**

가설 검증 단계에서 코드를 고치지 않고 스크립트로 3개 조합을 비교한 것이
비용과 시간을 크게 줄였다. **인덱스를 건드리는 일은 맨 마지막에.**

### 4-5. 역시 해결책처럼 보일 때를 조심

라운드 4의 (B) 실험이 그랬다. 접미사를 지우면 참고2 오염이 사라지지만
**찾아야 할 참고1도 같이 사라진다.** 오염원과 신호가 같은 단어를 공유하고 있었다.

"문제를 일으키는 것을 제거"가 아니라 **"의사가 다른 것을 분리"**가 답이었다.

## 5. 미해결로 남은 것

- **`review_settlement`의 예외 처리 범위** — `except RuntimeError`만 잡는데
  `embed_texts()`/`search()`는 RuntimeError로 감싸져 있지 않다. Qdrant 연결 실패나
  Jina 429가 배치 중간에 나면 루프 전체가 죽고 이미 처리된 건까지 유실된다.
- **`chunking.py`의 죽은 코드** — `detect_chunking_tier` / `detect_toc`가 실제
  파이프라인에서 미사용(디버그 API 전용), `extract_section_title`은 미사용 import.
- **`/review-settlement`의 검색 호출 증가** — 영수증 N건 × 검색 2회.
  비목이 같으면 쿼리도 같으므로 캐시 가능하지만, 현재 규모에서는 문제가 아니다.
- **증빙매칭의 배타적 배정 규칙 모델 미준수** — 같은 파일이 두 항목에
  `matched`로 배정되는 사례를 2회 재현. lite 모델의 지시 준수 한계.
