### 9. 증빙서류 자동매칭(`document_match`) 설계·구현
- 상황: 서류 컴플라이언스 기능의 스코프에 OCR 기반 증빙서류 첨부 여부 판정이 재포함되기로 확정.
- 행동: `/classify-receipt`를 4단계(추출→분류→컴플라이언스→매칭)로 확장. LLM 1회 호출로 필요서류 vs 첨부파일 매칭(M×N 루프 아님), `matched`/`missing`/`unclear` 3단계 판정 설계. "매칭 안 함"과 "매칭했는데 필요서류 목록 자체가 없음"을 sentinel로 구분.

- 근거: FINDINGS_2026-08-19_review_settlement_and_document_match.md §3

### 10. required_documents 오류 원인 — 4라운드 오진 끝에 진짜원인 규명
- 상황: 컴플라이언스 검색이 반환하는 `required_documents`가 비목에 따라 부정확, 같은 코드인데 실행 시점마다 결과가 다름.
- 행동: 원인 후보를 3번 잘못 짚음 — (1)"doc_tier가 검색랭킹에 미반영"(실측으로 반증), (2)"표가 청크 경계에서 잘림"(진짜 버그였으나 고치니 다른 항목이 회귀), (3)"짧은 청크가 강하니 행단위로 더 쪼개자"(더 악화, 새로운 오염 발견). 4번째에서 실측 데이터를 대조해 "검색 쿼리 하나에 목적이 다른 세 질문(한도/제출서류/불인정기준)이 섞여 있었다"는 진짜 원인을 특정.
- 결과: 쿼리를 목적별 2개로 분리 후 참고1(제출서류) top5 진입 4/6→6/6, 참고2(불인정기준) 오염 4/6→1/6, 국내여비 순위 19위→2위, 소모품비 10위→1위. 국내여비·소모품비가 동시에 top5에 든 것은 이번이 처음. 재임베딩 불필요(쿼리만 변경).

### 15. 분산의 진짜 원인 규명 및 해결 — 정보 부족이 진짜 원인

- 행동: 같은 이미지를 3번씩 태워 단계별 출력의 "동일성"(정확도 아님)을 비교(3장×3회=9콜). 성수주유소 영수증에서 추출(vendor/item/amount/date)은 완전 동일한데 분류(flag)만 "확인필요"/"지원불가"로 갈리는 것을 확인.

- 근거: FINDINGS_2026-08-28_variance.md §2, §3, §4
- 쓸 곳: "근본원인 규명", "temperature=0으로 안 되는 문제를 정보 제공으로 해결"

## 아직 못하는 것 (열린 문제)

- **영수증 평가셋이 협소** — 31장 중 `지원불가` 정답이 3건뿐이라 1건이 33%p. 게다가 그 3건이 정확히 taxonomy에 명시한 유류비·주차비라 leakage에 가까움. 새 영수증(렌터카/PC·노트북/귀금속/톨비/개인카드 결제) 수집이 선행돼야 하는데 미착수. (PROJECT_STATE.md "다음 할 일 #2")
- **렌터카·범용기자재(PC/노트북)·귀금속 조항 검증 0건** — 해당 유형 영수증이 평가셋에 없어 고정 검색쿼리가 이 조항을 끌어오는지 검증 자체가 불가능. (PROJECT_STATE.md #2, README §6)
- **`/chat` 답변 생성 품질 미측정** — retrieval(hit@1)만 측정됨. 답변 자체의 품질은 라벨도 채점 방법(LLM-judge/사람 채점)도 없어서 미착수. (PROJECT_STATE.md #3)
- **score로 no_answer를 못 가름** — no_answer 문항과 answerable 문항의 top1 score 차이가 거의 없어(위 숫자표 참조) 임계값 기반 로직이 이 데이터에서 작동 안 함. (PROJECT_STATE.md #4)
- **chat 미포함 2건 미해결** — c05(회의비 조항이 서로 다른 두 청크에 중복 존재), c10(참고1 제출서류표, 표 형식 검색 실패). 원인은 파악됐으나 해결책은 미적용. (PROJECT_STATE.md #5)
- **`/review-settlement` 미측정·UI 미노출** — `document_match`(증빙매칭) 배치 미연결, `except RuntimeError`만 잡아서 Qdrant/Jina 실패 시 배치 전체가 죽음, 프런트에 탭 자체가 없음. 2주 일정상 README에 "API만 존재"로 명시하고 넘김. (PROJECT_STATE.md #6, README §2)
- **`absolute_cap`(절대금액 캡) 구조적 미작동** — 수정하려면 taxonomy의 `sub_item` 출력을 바꿔야 해서 분류 단계 회귀 위험이 있고, 현재 평가셋은 이미 천장(100%)이라 회귀를 잡아낼 수 없음. 평가셋 확장 이후로 보류. (PROJECT_STATE.md #7)
- **r003 status variance 원인 미확인** — 숙박비 상한초과 케이스가 실행마다 `확인불가`(정답)↔`위반의심`으로 갈림. `classification.flag=확인필요`라 override 경로도 안 타서 원인 추적이 막혀 있음. (PROJECT_STATE.md #8)
- **override(컴플라이언스의 flag 뒤집기) 채택 0건** — 게이트 차단은 0건이 됐지만 채택도 0건. 현재 평가셋에 "분류=확인필요인데 컴플라이언스가 뒤집어야 하는" 케이스 자체가 없어 검증 불가. (PROJECT_STATE.md #9)
- **HWP 미지원** — PDF만 변환 가능. (README §2)
