## 1. `/review-settlement` 실행 검증

`/review-settlement`는 8/16 세션에 구현됐지만 이번 세션 전까지 **실제 HTTP 호출로 검증된 적이 없었음**(코드 리뷰/설계 확인만 있었음).

### 실행
영수증 3건(식비 지원불가 2건 + 숙박 정상 1건), `total_budget=5,000,000`으로 `curl -F`(파일명이 전부 숫자라 한글 인코딩 이슈 없음, `feedback_korean_curl_encoding.md` 메모리에 해당 안 됨) 호출.

### 결과
- 200 OK. 지원불가 2건 → `위반의심`/`required_documents: []`(의도대로), 숙박 정상 1건 → `확인불가`/`required_documents` 채워짐.
- `cap_violations`(시제품제작비 0%, 최소 50% 기준 미달) 정확히 잡힘.
- **개선점 발견**: 8/16 세션 기록엔 `required_documents`가 `national_eval_rule.pdf`의 일반 증빙목록만 나왔다고 남아있었는데, 이번 실행에선 `guiideline.pdf`의 [별지14호]/[별지11호](사업 특화 서식)까지 정확히 잡힘. 재현 조건이 명확히 다르진 않아서 우연인지 검색 스코어 변동인지는 불명 — 다음에 같은 현상이 재현되는지 관찰 필요.

## 2. Gemini 출력 음절 오타 원인규명

`review-settlement` 결과 중 한 항목의 `classification.reasoning`에서 이상한 문구 발견:

> "사업 관련 회의비 및 **현문성 묰품** 구매는 지원되지 않으며..."

정확한 원문(`config.py:122`, `RECEIPT_CATEGORY_TAXONOMY`에 박제됨): "사업 관련 회의비 및 **현물성 물품** 구매는 지급하지 아니한다"

### 조사
`unicodedata`로 문제 문자열의 코드포인트를 전수 확인 — 전부 정상 완성형 한글 음절(U+AC00~D7A3 범위, 정상 `HANGUL SYLLABLE ...` NAME 매칭). **인코딩/mojibake 버그 아님.**

- 물(mul) → 문(mun): 받침 ㄹ→ㄴ 치환
- 물(mul) → 묰(myok): 모음+받침 전체가 다른 음절로 치환(더 심함)
- 같은 문장에 "식비랫도"(존재하지 않는 조합)도 발견 — 동일 원인으로 추정
- 같은 배치의 다른 파일에서는 동일 문구가 정확히 인용됨 — **비결정적**(같은 system prompt, 같은 세션 내에서도 발생/미발생 갈림)

### 결론
모델(`gemini-3.5-flash-lite`)이 짧은 인용구를 재생성하는 과정에서 음절 단위로 오타를 내는 현상. 판정 결과(지원불가/위반의심) 자체는 정확했음 — 근거 텍스트 품질 문제이지 판단 로직 오류 아님.

### 이론적 연결
`document/FINDINGS_2026-08-07_gemini_conversion_truncation.md`에서 규명한 "lite 모델은 verbatim 전사를 신뢰할 수 없다"는 결론이 **다른 증상으로 재현됨**. 그때는 PDF 변환 시 문단 단위 요약/생략이었고, 이번엔 짧은 인용구의 음절 단위 치환 — 증상은 다르지만 "lite 모델 출력을 곧이곧대로 신뢰하면 안 된다"는 같은 결론으로 수렴. 별도 FINDINGS 문서는 안 만들고 이 문서와 DEV_LOG에만 기록(스코프가 작아서).

## 3. 증빙서류 자동매칭(`document_match`) 기능 구현

### 배경
서류 컴플라이언스 기능(③)의 스코프를 두고 대화 중 확인됨: "완성"의 의미가 **8/16에 명시적으로 제외했던 OCR 기반 증빙서류 첨부 여부 판정**을 다시 포함시키는 것으로 확정됨(사용자 지시로 스코프 재포함).

### 설계 → 구현 → 검증
전체 설계결정 6가지, 구현 파일별 변경사항, 검증 [1]~[7] 결과, 발견된 모델 이슈(한 파일=한 항목 배정 규칙 미준수), 미해결 이슈 3건은 **기술 스펙 문서(`docs/document_match.md`)에 상세 기록** — 이 문서는 사람이 읽는 요약이므로 핵심만:

- `/classify-receipt`가 4단계(추출→분류→컴플라이언스→매칭)로 확장됨. `supporting_docs`(선택, 다중 이미지/PDF)를 새로 받음.
- LLM 1회 호출로 필요서류 vs 첨부파일을 매칭(M×N 루프 아님), `matched`/`missing`/`unclear` 3단계 판정.
- "매칭 안 함"(`[]`)과 "매칭했는데 필요서류가 없어서 못 함"(`"(필요서류 목록 없음)"` sentinel)을 명확히 구분하도록 설계 — 검증 [4]에서 실제로 구분됨을 확인.
- 웹 UI(`static/index.html`)에도 반영, Playwright로 헤드리스 브라우저 실제 렌더링까지 확인.
- **미실행**: 실제 증빙서류 샘플([별지N] 등)이 `tests/test_receipts/`에 없어서 ground-truth 정확도 검증([2][3])은 못 함 — 다른 영수증 이미지를 대용으로 써서 파이프라인 동작 자체는 확인.
- **배치(`/review-settlement`) 미연결** — 여러 영수증에 증빙서류 묶음을 매핑하는 멀티파트 그룹핑 설계가 별도로 필요해서 다음 과제로 이월.
