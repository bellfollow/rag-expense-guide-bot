# 지시: override 게이트 + 검색 쿼리 fallback (수정 C)

## 배경 — 수정 B는 성공했다. 남은 2건의 원인이 확인됐다

| | 원본 | A 이후 | B 이후 |
|---|---|---|---|
| flag 출력 종류 | 2 | 1 (단일 수렴 붕괴) | 2 |
| 지원불가 recall | 0/3 | 0/3 | **2/3** |
| 확인필요 recall | 0/28 | 28/28 | **27/28** |
| macro recall | 0% | 50% | **82%** |

override 3건이 발동해 2건을 정확히 잡았다. 남은 문제는 두 가지이고,
**서로 다른 원인이므로 따로 고친다.**

---

## 문제 ① — override가 프롬프트 규칙을 지키지 않았다 (오탐 1건)

`r011`(카페 커피 영수증)에서 override가 잘못 발동했다.

```
citation:  "창업탐색비 집행 관리 가이드라인 [참고표] 참고 1. 창업탐색비 집행관련 제출서류"
reasoning: "...회의 목적의 지출인지 ... 명확히 알 수 없으므로 지출 목적과 참석자 등
            세부 내역을 확인해야 합니다."
override_flag: "지원불가"
```

인용한 것은 **제출서류 표**이지 금지 조항이 아니다. reasoning 자체가 "확인해야 한다"고
말하는데 override는 `지원불가`를 냈다. 자기모순이다.

컴플라이언스 프롬프트에 금지 표현 목록("지급하지 아니한다", "지원되지 않으며" 등)을
명시했는데도 지키지 않았다.

**→ 프롬프트를 더 강하게 쓰지 마라. 코드로 게이트하라.**
이 프로젝트의 「결정론 판단과 LLM 판단 분리」 원칙(금액 한도를 코드로 계산하는 것과 같은 이유)을
그대로 적용한다. "인용문에 금지 표현이 실제로 들어 있는가"는 문자열 검사로 확정할 수 있는
사실이지, LLM에게 물을 문제가 아니다.

### 수정 1-1 — `config.py`

`ABSOLUTE_CAP_RULES` 근처에 모듈 상수를 추가한다.

```python
# 컴플라이언스가 override_flag="지원불가"를 낼 때, 인용한 조항에 아래 표현 중 하나가
# 실제로 포함돼야만 override를 인정한다(pipeline.py에서 검사).
# LLM이 "제출서류 표"를 금지 조항으로 오인해 override를 낸 사례가 있어 코드로 게이트한다.
# "~할 수 있다", "~를 원칙으로 한다" 같은 재량 표현은 금지가 아니므로 목록에 넣지 마라.
PROHIBITION_MARKERS = [
    "지급하지 아니한다",
    "지원되지 않으며",
    "지원되지 않는다",
    "청구할 수 없다",
    "집행 불가",
    "집행이 불가",
    "구매가 불가능",
    "계상할 수 없다",
    "지급불가",
    "지급 불가",
    "사용할 수 없다",
]
```

### 수정 1-2 — `pipeline.py`

수정 B에서 넣은 override 블록에 **게이트 조건을 추가**한다. 요구사항:

- `override_flag == "지원불가"`이면서 **`citation`에 `PROHIBITION_MARKERS` 중 하나가
  부분문자열로 포함될 때만** override를 적용한다
- 게이트에 걸려 무시된 경우, `compliance["override_rejected"]`에 이유를 남겨라
  (측정할 때 "게이트가 몇 번 막았는지"를 봐야 한다. 조용히 버리지 마라)
- `citation`이 없거나 빈 문자열이면 게이트 통과 실패로 처리한다
- 기존 override 성공 경로(`flag_before_override`, `override_reason` 기록)는 그대로 둔다

블록 전체가 15줄을 넘지 않게 하라. 헬퍼 함수를 만들지 마라.

## 문제 ② — 검색 쿼리가 무의미해서 조항을 못 가져온다 (놓친 1건)

같은 주유소 영수증 2장인데 결과가 갈렸다.

```
r002  citation: "유류비는 지원되지 않으며..."   → override 성공
r001  citation: (비어있음)                       → 조항 자체를 못 찾음
```

원인은 `classify_receipt()`의 검색 쿼리 구성이다.

```python
sub_item = classification.get('sub_item') or ''
queries = [f"{sub_item} 한도 사용기준", f"{sub_item} 제출서류"]
```

`r001`은 분류가 `sub_item="해당없음"`을 냈고, 그 결과 실제 검색어가
**`"해당없음 한도 사용기준"`** 이 되었다. 의미 없는 쿼리라 관련 조항이 상위에 오르지 않는다.

이것은 수정 A의 부작용이다. Rule 3에서 `확인필요 + 해당없음` 조합을 허용했는데,
그 조합이 검색을 무력화한다는 점을 고려하지 않았다. 현재 31건 중 **29건이 `해당없음`**이므로
대부분의 검색이 헛돌고 있다. `r002`가 조항을 찾은 것이 오히려 우연에 가깝다.

### 수정 2 — `pipeline.py` 검색 쿼리 fallback

`sub_item`이 `"해당없음"`이거나 비었을 때는, **영수증에서 추출한 실제 내용으로 검색**한다.

요구사항:

- 판정 기준: `sub_item`이 `"해당없음"`이거나 falsy일 때
- 그 경우 `extracted`의 `item`과 `vendor`를 사용해 쿼리를 만든다
- 목적 분리 원칙을 유지하라 — **한 쿼리에 여러 목적을 섞지 마라.**
  (이전에 "한도 + 제출서류 + 불인정기준"을 한 쿼리에 넣어 검색 품질이 무너진 전례가 있다)
  최소 다음 두 목적을 각각 별도 쿼리로 둔다:
  1. 이 지출이 금지·불인정 대상인지
  2. 어느 비목에 해당하는지
- 기존 `flag == "지원불가"` 분기와 정상 분기의 동작은 **바꾸지 마라.**
  이번에 추가하는 것은 `해당없음` 분기 하나뿐이다
- 쿼리 병합 로직(`per_query_k`, 올림 나눗셈, score 기준 dedup)은 그대로 재사용하라.
  새로 짜지 마라

## 검증

측정은 내가 직접 돌린다. 평가셋은 이 레포에 없다(실물 영수증이라 커밋하지 않음).
**약식 검증을 하지 마라.** 수정만 하고 대기하라.

내가 확인할 기준:

| 항목 | 현재 (B) | 성공 조건 |
|---|---|---|
| override 오탐 | 1건 (r011) | **0건** |
| override 게이트 차단 | — | 최소 1건 기록될 것 (r011이 막혔는지) |
| 놓친 지원불가 | 1건 (r001) | **0건** |
| 확인필요 recall | 27/28 (96%) | **27/28 이상** |
| 지원불가 recall | 2/3 (67%) | **3/3 목표** |
| macro recall | 82% | **상승** |
| 금액·날짜 | 29/31, 30/31 | **변동 없음** |

**주의:** 수정 ②는 검색 쿼리를 바꾸므로 `sub_item`이 `해당없음`인 29건 전부의
컴플라이언스 입력이 달라진다. 부작용 범위가 넓다.
`확인필요 recall`이 떨어지면 검색이 엉뚱한 금지 조항을 물어와 override가 남발된 것이므로,
그 경우 ②를 되돌리고 ①만 유지하는 편이 낫다.
