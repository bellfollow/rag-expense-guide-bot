# 지시: 컴플라이언스가 flag를 승격할 수 있게 (수정 B)

## 배경 — 수정 A는 실패했다

Rule 2~5 교체 후 재측정 결과:

| 지표 | A 이전 | A 이후 |
|---|---|---|
| flag 정확도 | 0/31 (0%) | 28/31 (90%) |
| 모델이 낸 flag 종류 | `지원불가`×28, `확인필요`×3 | **`확인필요`×31 (단일)** |
| 다수결 베이스라인 | — | **28/31 (90%)** |

**90%는 성능이 아니다.** 정답 분포가 `확인필요` 28 / `지원불가` 3이므로,
아무 판단 없이 `확인필요`만 찍어도 정확히 90%가 나온다. 실제로 모델은 31건 전부
`확인필요`를 냈다. 단일 클래스로 완전히 수렴했다.

수정 전(전부 `지원불가`)과 **구조적으로 동일한 실패**이며 방향만 뒤집혔다.

### 원인 — Rule 4-1이 물리적으로 실행 불가능한 요구다

```
4-1. "지원불가"는 영수증에 실제로 인쇄된 사실만으로 금지 조항에 걸릴 때만 쓴다.
```

그런데 **분류 단계는 RAG를 쓰지 않는다.** 참조할 수 있는 금지 조항은
`RECEIPT_CATEGORY_TAXONOMY` 주의사항에 있는 회의비·현물성물품 항목 하나뿐이고,
Rule 4-3이 그마저 "식당 영수증엔 회의 여부가 인쇄되지 않으니 그것만으로 판정하지 마라"로
막았다. **결과적으로 `지원불가`를 낼 수 있는 경로가 전부 닫혔다.**

Rule 2~5는 되돌리지 마라. 과잉 거절과 인용-결론 모순은 실제로 해소됐고
(confidence가 `high`에서 `low`/`medium`으로 내려갔다), 문제는 출구가 없다는 것이다.

## 이번 수정의 근거 — 정답 조항은 이미 검색되고 있다

`r001`(주유소 영수증)의 컴플라이언스 단계 citation:

```
"자가 이용 시 동일구간 내 대중교통비 정액을 기준으로 집행한다.
 유류비는 지원되지 않으며..."
```

`r004`(주차비 영수증):

```
"출장지 내에서 소요되는 교통비(버스, 지하철, 택시 요금 등), 주차비 등의
 각종 비용은 일비에 포함되므로 별도로 청구할 수 없다."
```

**RAG는 정답을 찾아냈다.** 그런데 `flag`는 상류(분류 단계)에서 이미 확정돼 있고,
`GEMINI_RECEIPT_COMPLIANCE_MODEL`의 Rule 0은 단방향이다:

> "[분류 결과]의 flag가 '지원불가'면 ... compliance_status를 '위반의심'으로 판정하고"

flag → compliance 방향만 있고 역방향이 없다. 그래서 컴플라이언스가 금지 조항을
손에 쥐고도 판정을 뒤집지 못한다.

**이번 수정은 그 역방향 경로를 뚫는 것이다.** 분류 단계에 RAG를 붙이지 않는다.

## 수정 1 — `config.py` 컴플라이언스 프롬프트

`GEMINI_RECEIPT_COMPLIANCE_MODEL`의 system_instruction에 **Rule 1 바로 다음**에
아래를 삽입한다. 기존 Rule 0, 2~5는 그대로 두고 번호만 밀어라.

```
1-2. [분류 결과]의 flag가 "정상" 또는 "확인필요"라도, [참고 규정]에 이 지출을
     명시적으로 금지하는 조항이 있고 그 조항이 이 영수증에 직접 적용된다면
     compliance_status를 "위반의심"으로 판정하고 override_flag를 "지원불가"로 설정하라.
     분류 단계는 규정을 검색하지 않으므로, 규정에 근거한 금지 판단은 이 단계의 책임이다.

     "명시적 금지"란 규정 원문에 다음과 같은 단정적 금지 표현이 있는 경우를 말한다:
       "지급하지 아니한다", "지원되지 않으며", "청구할 수 없다", "집행 불가",
       "구매가 불가능하다", "계상할 수 없다", "지급불가"
     "~할 수 있다", "~를 원칙으로 한다", "필요시" 같은 재량·조건 표현은 금지가 아니다.

     "직접 적용"이란 조항이 금지하는 대상과 이 영수증의 지출 대상이 같다는 뜻이다.
     예: 조항이 "유류비는 지원되지 않으며"인데 영수증이 주유소 휘발유 결제 → 직접 적용.
     조항이 다른 비목에 관한 것이거나 적용 여부를 추정해야 한다면 override_flag는 null로 두어라.

     override_flag를 설정할 때는 citation에 그 금지 조항 원문을 그대로 인용하라.
     금지 조항을 찾지 못했거나 적용이 불확실하면 override_flag는 반드시 null이다.
```

출력 JSON에 `override_flag` 키를 추가한다. 기존 키는 이름·개수 모두 유지한다.

```
{"compliance_status": "준수|위반의심|확인불가", "compliance_notes": "...", "citation": "...",
 "hierarchy_note": "...", "required_documents": [...], "override_flag": "지원불가|null"}
```

## 수정 2 — `pipeline.py` 배선

`classify_receipt()` 안, 컴플라이언스 응답을 파싱한 직후 · `absolute_cap` 계산 **이전**에
override를 반영한다.

요구사항:

- `compliance["override_flag"] == "지원불가"`일 때만 `classification["flag"]`를 갱신한다
- 갱신 시 `classification["main_category"]`와 `sub_item`도 `"해당없음"`으로 맞춘다
  (분류 프롬프트 Rule 2와 일관되게)
- **덮어쓰기 흔적을 남겨라.** 원래 flag를 `classification["flag_before_override"]`에 보존하고,
  `classification["override_reason"]`에 컴플라이언스의 citation을 넣어라.
  측정할 때 "분류가 맞춘 것"과 "컴플라이언스가 구제한 것"을 구분해야 한다
- `override_flag`가 없거나 null이면 아무것도 하지 않는다 (기존 동작 유지)
- `absolute_cap` 계산이 갱신된 `sub_item`을 쓰게 되므로 순서를 반드시 지켜라

코드는 10줄 안쪽이어야 한다. 헬퍼 함수나 클래스를 만들지 마라.

## 검증

측정은 내가 직접 돌린다. 평가셋은 이 레포에 없다(실물 영수증이라 커밋하지 않음).
**약식 검증을 하지 마라.** 수정만 하고 대기하라.

내가 확인할 기준은 이것이다:

| 항목 | 현재 | 성공 조건 |
|---|---|---|
| 모델이 낸 flag 종류 | `확인필요` 1종 | **2종 이상** (단일 수렴 탈출이 최우선) |
| 놓친 지원불가 | 3건 | **감소** (r001·r002·r004) |
| `확인필요` 클래스 recall | 28/28 (100%) | **26/28 이상 유지** (과잉 거절 재발 방지) |
| flag 정확도 | 90% (=베이스라인) | 베이스라인 **초과** |
| 금액·날짜 | 29/31, 30/31 | **변동 없음** |

`확인필요` recall이 크게 떨어지면 과잉 거절이 재발한 것이므로 순이득이 아니다.
**단일 클래스 수렴 탈출과 확인필요 유지, 둘 다 만족해야 성공이다.**
