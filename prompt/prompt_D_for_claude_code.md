# 지시: 검색 fallback 롤백 + 게이트 일관성 수정 (수정 D)

## 배경 — 수정 C는 절반만 성공했다

C에서 두 가지를 넣었다. **①(override 게이트)은 성공, ②(검색 fallback)는 순손실이다.**

| | B | C |
|---|---|---|
| override 오탐 | 1건 | **0건** ✅ ①의 성과 |
| 지원불가 recall | 2/3 (67%) | **1/3 (33%)** ↓ ②의 손실 |
| 확인필요 recall | 27/28 | 28/28 |
| **macro recall** | **82%** | **67%** ↓ |
| status | 94% | **81% (다수결 베이스라인 90% 이하)** ↓ |

### ②가 실패한 이유 — vendor가 검색을 오염시켰다

`r002`(주유소)는 B에서 `"유류비는 지원되지 않으며..."`를 정확히 인용했다.
C에서는 `citation`이 **빈 문자열**로 나왔다. 조항 자체를 검색해오지 못했다는 뜻이다.

```python
f"{item} {vendor} 지급 불가 불인정기준"
→ "휘발유 성수주유소 지급 불가 불인정기준"
```

`vendor`("성수주유소")는 지침 문서 어디에도 없는 고유명사다. 임베딩 공간에서
쿼리 벡터를 규정 조항과 무관한 방향으로 끌고 간다.
이 프로젝트에서 이미 확인된 실패 패턴이다(고유명사가 검색 품질을 무너뜨림).

**판단 실수는 내 쪽에 있었다.** 되돌림 조건을 "확인필요 recall이 떨어지면"으로 걸었는데,
실제로는 확인필요 recall이 **올랐고**(아무것도 잡지 않아서) 지원불가 recall이 무너졌다.
macro recall로 판정했어야 했다.

## 수정 2 — `pipeline.py` 게이트 일관성

게이트가 `override_flag`를 막았는데 `compliance_status`는 그대로 두어
판정이 서로 어긋난다.

C 결과에서 `compliance_status="위반의심"`이 5건인데 최종 `flag="지원불가"`는 1건이었다.
게이트에 막힌 4건(`r007`, `r015`, `r017`, `r020`)이 `위반의심`으로 남은 것이다.
"지급 불가 항목은 아니지만 위반은 의심된다"는 상태가 되는데, 그 4건은 모두
컴플라이언스가 **금지 조항이 아닌 것을 금지 조항으로 오인**해서 나온 판정이므로
`위반의심`도 근거가 없다.

기존 게이트 `else` 블록(차단 경로)에 다음을 추가한다:

- `compliance["compliance_status"]`가 `"위반의심"`이면 `"확인불가"`로 되돌린다
- 되돌리기 전 값을 `compliance["status_before_gate"]`에 보존한다
  (조용히 바꾸지 마라 — 측정 시 게이트가 status에 얼마나 개입했는지 봐야 한다)
- `compliance_status`가 `"위반의심"`이 아니면 건드리지 마라
  (`"준수"`나 `"확인불가"`는 override와 무관하게 나온 판정일 수 있다)
- 기존 `override_rejected` 기록은 그대로 유지한다

추가되는 코드는 4줄 이내여야 한다.
